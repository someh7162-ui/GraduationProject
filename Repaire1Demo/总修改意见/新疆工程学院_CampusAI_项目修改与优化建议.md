# 新疆工程学院 Campus AI 项目修改与优化建议

> 项目：GraduationProject  
> 当前定位：面向新疆工程学院的校园智能信息服务系统  
> 建议用途：毕业设计开发计划、系统优化清单、后续迭代说明  
> 更新时间：2026-09-21

---

## 1. 项目当前定位建议

目前项目已经不再只是单一的“校园信息推荐系统”，现有功能已经覆盖：

- 用户注册与登录
- 学院、专业、年级等学生身份信息
- 兴趣初始化与用户画像
- 校园信息个性化推荐
- 用户浏览、收藏、报名等行为反馈
- 校园知识库检索
- RAG 智能问答
- 学业档案管理
- 成绩单导入
- OCR 成绩识别
- 班级成绩排名
- 奖学金政策管理
- 奖学金资格核验
- 数据来源追踪
- 基础权限控制

因此建议将项目统一定位为：

> **面向新疆工程学院的校园智能信息服务系统设计与实现**

也可以采用更突出技术路线的题目：

> **基于用户画像与 RAG 的校园智能信息服务系统设计与实现**

系统展示名称可以继续使用：

> **Campus AI**

这样能够统一“校园推荐、知识问答、学业服务、政策核验”等现有功能，避免论文题目与实际系统功能不一致。

建议后续按照以下三个优先级推进。

| 优先级 | 说明 |

# 3. P0：必须修改

## 3.1 学院与专业必须进行后端校验

目前学院和专业主要依赖前端填写或选择，如果只在前端实现学院与专业联动，用户仍然可以绕过前端直接调用接口提交不存在的学院和专业。

例如错误数据：

```json
{
  "college": "火星工程学院",
  "major": "御剑飞行专业"
}
```

因此后端也必须拥有新疆工程学院学院与专业数据。

建议新增目录：

```text
app/
└── catalog/
    ├── __init__.py
    ├── xjie_academics.py
    └── api.py
```

建议提供接口：

```http
GET /catalog/colleges
GET /catalog/colleges/{college_code}/majors
```

注册时需要执行以下校验：

```text
学院是否存在
    ↓
专业是否存在
    ↓
专业是否属于该学院
    ↓
通过后才允许注册
```

这样可以保证数据库中的学院与专业数据真实、统一。

---

## 3.2 注册页面改为“学院 → 专业”联动选择

学生注册时不应该手工输入学院与专业。

建议注册顺序：

```text
身份
 ↓
学院
 ↓
专业
 ↓
年级
```

用户选择学院以后，只显示该学院对应专业。

例如：

```text
信息工程学院
  ├─ 计算机科学与技术
  ├─ 数据科学与大数据技术
  ├─ 通信工程
  ├─ 物联网工程
  └─ 数字媒体艺术
```

这样能够避免以下脏数据：

```text
信息学院
信息工程
信息工程学院
信工学院
```

同时能够为后续：

- 专业推荐
- 学院推荐
- 教务服务
- 奖学金政策匹配
- 学生画像

提供可靠基础数据。

---

## 3.3 禁止普通用户自行注册辅导员和管理员身份

当前注册页面如果允许用户自行选择：

```text
学生
辅导员
活动组织者
```

未来一旦不同角色拥有不同权限，就可能产生越权问题。

建议角色划分为：

```text
student         学生
teacher         教师
counselor       辅导员
academic_admin  教务管理员
admin           系统管理员
```

建议：

- 普通注册只能注册学生账号；
- 教师、辅导员、教务管理员由管理员创建；
- 或提交身份申请后由管理员审核；
- 系统管理员不得开放自助注册。

这样后续可以在论文中作为 RBAC 权限控制设计进行说明。

---

## 3.4 修正首次登录流程

目前登录完成后直接进入 AI 问答页面，与 README 中“首次登录选择兴趣模块”的设计存在不一致。

建议统一为：

```text
用户登录
   ↓
是否完成兴趣初始化
   ├─ 否 → 兴趣选择页
   └─ 是 → 推荐首页
```

推荐逻辑：

```javascript
if (!user.onboarding_completed) {
  page = 'onboarding'
} else {
  page = 'home'
}
```

这样注册、兴趣画像和推荐流程才能形成完整闭环。

# 4. P1：建议重点完成

## 4.1 学院和专业采用代码化存储

目前数据库直接保存中文名称，例如：

```text
college = 信息工程学院
major = 计算机科学与技术
```

建议增加稳定编码：

```text
college_code
college_name

major_code
major_name
```

例如：

```text
college_code = IE
college_name = 信息工程学院

major_code = 080901
major_name = 计算机科学与技术
```

数据库真正关联时使用代码，前端展示中文名称。

好处：

- 学院改名时历史数据仍然稳定；
- 专业调整学院归属时更容易迁移；
- 方便统计；
- 方便后续建立学院表和专业表。

## 4.2 推荐算法需要进一步规范化

当前推荐系统已经综合使用：

- 用户兴趣
- 用户行为
- 学院
- 专业
- 年级
- 用户角色
- 内容发布时间
- 活动截止时间

这是项目很重要的核心功能。

目前综合评分大致可以表达为：

```text
Score =
0.55 × 兴趣匹配度
+ 0.20 × 行为画像得分
+ 0.15 × 内容新鲜度
+ 0.10 × 截止日期紧迫度
```

建议保留这种轻量级、可解释的混合推荐方式，不建议为了复杂而引入深度学习。

论文中可以设计三组实验：

```text
方案 A：
仅兴趣标签推荐

方案 B：
兴趣 + 学院 + 专业 + 年级

方案 C：
兴趣 + 身份画像 + 用户行为 + 时间因素
```

建议评估指标：

```text
Precision@K
Recall@K
Hit Rate@K
NDCG@K
```

这样可以证明混合推荐策略相比基础推荐有所改进。

---

## 4.3 用户行为需要区分权重

目前：

```text
view
click
favorite
share
register
```

都属于正反馈，但行为强度并不相同。

建议赋予不同权重，例如：

| 行为 | 建议权重 |
| --- | ---: |
| view | +0.1 |
| click | +0.2 |
| favorite | +0.6 |
| share | +0.7 |
| register | +1.0 |
| dismiss | -0.8 |

可以定义：

```text
BehaviorScore =
Σ（行为权重 × 对应内容标签相关度）
```

这样推荐算法更合理，也更方便在论文中解释。

## 4.4 删除前端写死的“92%匹配度”

当前前端存在类似：

```vue
<strong>{{ items.length ? '92%' : '—' }}</strong>
```

该数字并不是真实计算结果，不建议在最终系统保留。

可以改成真实的：

> 今日兴趣匹配率

例如：

```text
Top 10 推荐结果中，
命中至少一个用户兴趣标签的内容数
÷
Top 10 推荐内容数
```

如果 10 条推荐中有 8 条命中兴趣标签：

```text
8 / 10 = 80%
```

页面显示：

> 今日兴趣匹配率：80%

这样指标有真实数据依据。

- 年级

但 RAG 问答目前主要从所有已发布内容中检索。

```text

```

统一权限规则可以避免：

这种数据权限不一致问题。

# 5. P2：进一步优化

## 5.1 缓存 TF-IDF 索引

当前 RAG 每次问答可能重新执行：

```python
TfidfVectorizer(...)
fit_transform(docs)
```

随着校园知识库增大，效率会下降。

建议修改为：

```text
校园数据导入
     ↓
构建 TF-IDF 索引
     ↓
缓存 vectorizer
     ↓
缓存 document matrix
     ↓
用户问题仅执行 transform
```

只有知识库发生变化时才重新建立索引。

这样可以明显提升问答响应速度。

---

## 5.2 保留轻量级 RAG，不必过度复杂化

当前结构：

```text
用户问题
   ↓
TF-IDF
   ↓
余弦相似度
   ↓
Top K 校园资料
   ↓
DeepSeek
   ↓
带来源回答
```

对于本科毕业设计已经足够。

推荐继续保留：

- 无 API Key 也可使用本地检索；
- 相似度阈值拒答；
- 返回来源链接；
- 返回来源部门；
- 返回相似度；
- 大模型只能依据检索内容回答。

不建议为了复杂度额外引入大型向量数据库、知识图谱或多智能体。

---

## 5.3 增加来源可信度字段

建议校园内容增加：

```text
source_type
source_authority
last_verified_at
effective_from
effective_to
```

例如：

```json
{
  "source_type": "official_website",
  "source_authority": "新疆工程学院教务处",
  "last_verified_at": "2026-09-21"
}
```

AI 问答可以显示：

```text
来源：新疆工程学院教务处
更新时间：2026-09-21
```

有助于提升知识库可信度。

---

## 5.4 JWT Secret 不允许使用默认值

目前类似：

```python
JWT_SECRET = os.getenv("JWT_SECRET", "dev-secret")
```

生产或毕业答辩版本不建议保留默认密钥。

建议：

```python
JWT_SECRET = os.getenv("JWT_SECRET")

if not JWT_SECRET:
    raise RuntimeError("JWT_SECRET 未配置")
```

开发环境在 `.env.example` 中提供配置说明即可。

---

## 5.5 限制 CORS

当前类似：

```python
allow_origins=["*"]
```

建议最终限制为实际前端地址：

```text
http://127.0.0.1:5173
http://localhost:5173
```

部署以后再添加正式域名。

---

## 5.6 数据库暂时不需要大规模重构

目前以下字段：

```text
target_roles

target_majors
target_grades
tags
```

使用 TEXT + JSON 存储。

本科毕设阶段可以继续保留，不建议现在为了数据库范式进行大规模重构。

建议优先正式化的只有：

```text
学院
专业
```

后续可增加：

```text
colleges
majors
```

两张基础表。

# 10. 系统权限建议

建议角色结构：

| 角色 | 主要权限 |
| --- | --- |
| student | 个人资料、推荐、问答、个人学业数据 |
| teacher | 教学相关功能 |
| counselor | 所负责班级的学生与成绩信息 |
| academic_admin | 教务、政策、学院相关管理 |
| admin | 系统级管理 |

推荐权限模型：

```text
RBAC
+
Data Scope
```

例如：

```text
学生：
user_id = current_user.id

辅导员：
class_id in managed_classes

学院管理员：
college_code = current_user.college_code
```

# 12. 不建议继续增加的功能

当前项目已经具有足够的毕业设计工作量。

现阶段不建议继续加入：

- 人脸识别
- YOLO 目标检测
- 区块链
- 微服务架构
- Kafka
- Redis 集群
- Elasticsearch 集群
- 知识图谱
- 多智能体
- 自己训练大语言模型

原因是这些模块和校园智能服务主线关联不强，容易让项目变成“功能堆砌”。

建议原则：

> **做深比做多更重要。**

# 15. 总结

当前项目已经具备比较完整的毕业设计基础，主要问题已经不是“功能太少”，而是：

1. 数据口径需要统一；
2. 学院专业需要正规化；
3. 用户角色和权限需要完善；
4. 推荐算法需要更有理论依据；
5. RAG 与推荐系统需要共享数据权限；
6. 系统指标必须使用真实计算值；
7. 项目名称、README、论文和实际功能需要统一；
8. 各模块需要从“独立功能”进一步整合为完整业务流程。

后续开发的核心原则建议确定为：

> **真实数据、统一身份、可解释推荐、可信问答、权限安全、完整闭环。**

最终形成一个面向新疆工程学院实际校园场景的：

> **Campus AI 校园智能信息服务系统**
